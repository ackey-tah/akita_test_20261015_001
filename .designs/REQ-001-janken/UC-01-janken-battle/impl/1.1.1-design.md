## 1. 実装方針

`packages/shared-kernel/src/` に、業務 module が共通で使うエラーの基底とログ出力を置く（rules/development の「Logger ルール」「エラーハンドリングルール」、rules/architecture の「モジュラモノリス境界」）。

- **`DomainError`**（抽象クラス、`Error` を継承）
  - 継承クラスが `packageCode`（module を識別する英語 snake_case）を固定し、コンストラクタで module-local な `errorCode` と英語の `detail` を受ける
  - `code` は `"<packageCode>.<errorCode>"`。画面や調査で 1 つの文字列として扱うための組み合わせ
  - `message` には `detail` を入れ、`name` には継承クラスの名前を入れる。ログ出力はしない（ログは throw する側が出す）
  - 型引数 `TErrorCode extends string` で、継承クラスの ErrorCode の union を `errorCode` の型に流す
- **`Logger`**（interface）: `debug` `info` `warn` `error` の 4 メソッド。引数は日本語の `message` と、原因調査用の任意の `context`（`LogContext = Readonly<Record<string, unknown>>`）。`LogContext` も同じファイルに置く（Logger の契約の一部）
- **`getLogger` / `setLogger`**（`getLogger.ts`）: 処理側が呼ぶ共通の取得口。既定は `ConsoleLogger`。`setLogger` は composition root とテストが差し替えに使い、引数なしで既定に戻す。module 内の変数で 1 つだけ保持する
- **`ConsoleLogger`**: レベルに対応する `console.debug/info/warn/error` に `message` と `context` を渡す。`error` だけ、context に `stack` が無ければ呼び出し元の stack を補う
- **`MemoryLogger`**: テストで出力を確かめるための蓄積実装。`entries()` で `{ level, message, context }` の配列（コピー）を返し、`clear()` で空にする。`error` の stack の補い方は `ConsoleLogger` と同じ
- **stack の補い方**（`callerStack.ts` の関数 `withCallerStack(context, loggerMethod)`）: `Error.captureStackTrace` の第 2 引数に logger の公開メソッドを渡し、そのメソッド自身とそれより内側の frame を落とす。`captureStackTrace` が無い実行環境（V8 以外のブラウザ）では `new Error().stack` の先頭行（`Error`）だけを落とす。context に `stack` があれば context をそのまま返す（上書きしない）
- **`index.ts`**: 上記の公開物を named export する（`withCallerStack` は logger 実装の内部なので export しない）

## 4. テスト計画

観測点は単体テスト（受け入れ基準 ID は置かない）。

| テスト | 確かめること |
| --- | --- |
| `DomainError.test.ts` | テスト用の継承クラスで、`packageCode`・`errorCode`・`detail`・`code`・`message`・`name` が決まること。`Error` と `DomainError` の `instanceof` が成り立つこと |
| `getLogger.test.ts` | 既定が `ConsoleLogger` であること、`setLogger` で差し替えた logger が返ること、引数なしの `setLogger` で既定に戻ること |
| `ConsoleLogger.test.ts` | 4 レベルが対応する `console` のメソッドに message と context を渡すこと。`error` で stack が補われ、先頭の frame が logger の内部ではなく呼び出し元であること。context の `stack` を上書きしないこと |
| `MemoryLogger.test.ts` | 4 レベルが順に蓄積されること、`entries()` が内部配列のコピーであること、`clear()`、`error` の stack の補い方 |
| `callerStack.test.ts` | logger メソッドの frame を落とすこと、既存の `stack` を上書きしないこと、`captureStackTrace` が無い環境の代替経路 |

shared-kernel は domain / application ではないので 100% 閾値の対象外だが、分岐はすべてテストで通す。

## 5. リスク・注意点

- stack の frame 判定は実行環境（V8）依存。テストは「先頭の frame にテスト関数の名前が現れる」「logger の公開メソッド名が現れない」で確かめ、frame の文字列全体には依存しない
- `setLogger` はモジュール内の状態を書き換えるため、テストは `afterEach` で既定に戻す

## 逸脱

- **`error` を arrow function のプロパティにした**（`ConsoleLogger`・`MemoryLogger`）。stack を切る境界として自分自身を `withCallerStack` に渡すため。prototype のメソッドを値として渡すと lint（unbound-method）が this を失う書き方として止める
- **`rules/testing/project.md` にカバレッジ除外コメントの書き方を追記した**。`callerStack.ts` の到達困難な分岐（stack を持たない実行環境）を除外する際、`@preserve` が無いと Vitest 4 で除外が効かないと分かったため。後続の段で同じ手戻りを避ける
- **`callerStack.ts`・`callerStack.test.ts` を足した**（索引では 10 件、実際は 12 件）。stack を補う処理を `ConsoleLogger` と `MemoryLogger` の両方が使う。どちらかに置くともう一方がそのクラスに依存し、1 クラス 1 ファイルの原則（rules/development）とも合わないため、関数として分けた

## 修正ループの記録

- 1 周目のレビューで収束（要修正の指摘なし）。minor のうち次を任意で直した
  - テストの後片付けで `Error.captureStackTrace` を property descriptor ごと元に戻す
  - `captureStackTrace` が無い環境のテストで、呼び出し元の frame が残ることまで確かめる
  - `ConsoleLogger` は context が無いとき message だけを出す（ブラウザのコンソールに `undefined` が並ばないように）
- 見送った minor
  - 非 V8 ブラウザで logger 内部の frame が先頭に残る: 落とす段数を固定すると、呼び出し経路（`error` の arrow function・`withCallerStack`・`callerStack`）を変えたときに黙って呼び出し元の frame まで落とす。呼び出し元の frame を失わないことを優先した
  - 本番ビルドの minify で `DomainError` の `name` が短縮される: 継承クラスを作る 1.2.1（`JankenError`）の設計で扱う
