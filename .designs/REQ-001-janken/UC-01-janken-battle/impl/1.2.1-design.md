# 設計メモ: 1.2.1 手と勝敗

> 置き場: `.designs/REQ-001-janken/UC-01-janken-battle/impl/1.2.1-design.md`
> 実装ループの設計工程の成果物です。タスクの観測点・入力は [tasks.md](../tasks.md)、モデルは [docs/domain/janken/hand-手と勝敗.md](../../../../docs/domain/janken/hand-手と勝敗.md) にあります。

## 1. 実装方針

### domain（`packages/janken/src/domain/hand/`）

- **`HandKind`**: `"rock" | "scissors" | "paper"` の union 型。手の種類の実値を知っているのは `Hand` だけで、外では DTO 変換にだけ使う
- **`OutcomeKind`**: `"win" | "lose" | "draw"` の union 型
- **`Hand`**（Value Object）
  - 状態は `#kind: HandKind`。コンストラクタは private にし、factory からだけ作る
  - `rock()` `scissors()` `paper()`: 各手を返す
  - `pickByRandomValue(randomValue)`: 0 以上 1 未満の値を 3 等分し、`[0, 1/3)` をグー、`[1/3, 2/3)` をチョキ、`[2/3, 1)` をパーにする（`Math.floor(randomValue * 3)` で並び `[rock, scissors, paper]` の添字にする）。範囲外と `NaN` は、error log を出してから `JankenError("random_value_out_of_range")` を throw する
  - `against(opponent)`: 自分が勝つ相手の手の種類（グー → チョキ、チョキ → パー、パー → グー）を `Hand` 自身が持つ。同じ手ならあいこ、自分が勝つ相手なら勝ち、それ以外は負け
  - `equals(other)`・`kind()`
- **`Outcome`**（Value Object）
  - 状態は `#kind: OutcomeKind`。コンストラクタは private
  - `win()` `lose()` `draw()`・`isDecided()`（あいこでなければ true）・`equals(other)`・`kind()`

### errors（`packages/janken/src/errors/`）

- **`JankenErrorCode`**: janken module の ErrorCode の union 型。この段では `"random_value_out_of_range"` だけ。1.3.1・1.4.1 が値を足す
- **`JankenError`**: `DomainError<JankenErrorCode>` を継承し、`packageCode = "janken"` を固定する。`name` を `"JankenError"` と明示する。1.1.1 のレビューで、`DomainError` が `new.target.name` で入れる名前は本番ビルドの minify で短縮されると分かったため、継承クラスで文字列として固定する

## 4. テスト計画

観測点は domain の単体テスト。受け入れ基準 ID は置かない（UC-01 要件 3・4 の検証は 1.6.1 の UI 結合テスト）。`describe` は図の公開メソッド名にする（引数なしの getter `kind()` は各 factory のテストの中で確かめる）。

| テスト | `describe` | 確かめること |
| --- | --- | --- |
| `Hand.test.ts` | `rock` `scissors` `paper` | 種類がそれぞれグー・チョキ・パーの手を返す |
| | `pickByRandomValue` | 境界値: 0 → グー、1/3 の直前 → グー、1/3 → チョキ、2/3 の直前 → チョキ、2/3 → パー、1 の直前（`1 - Number.EPSILON`）→ パー。拒否: 負の値・1・`NaN` は `JankenError`（`random_value_out_of_range`）で、error log に乱数値が出る |
| | `against` | 3 × 3 の全組み合わせ（勝ち 3・負け 3・あいこ 3）を表で |
| | `equals` | 同じ種類は等しい、違う種類は等しくない |
| `Outcome.test.ts` | `win` `lose` `draw` | 種類がそれぞれ勝ち・負け・あいこ |
| | `isDecided` | 勝ち・負けは true、あいこは false |
| | `equals` | 同じ種類は等しい、違う種類は等しくない |
| `JankenError.test.ts` | `constructor` | `packageCode` が `janken`、`name` が `JankenError`、`code` が `janken.<errorCode>`、`DomainError` である |

domain は 100% 必須。`HandKind.ts`・`OutcomeKind.ts`・`JankenErrorCode.ts` は型だけで実行コードを持たない。

## 5. リスク・注意点

- 浮動小数の境界: `1/3` と `2/3` は 2 進で正確に表せない。テストは `1 / 3` と `2 / 3` をそのまま渡したときの結果（`Math.floor` で 1・2）と、その直前の値（`Math.nextDown` 相当として `x - Number.EPSILON`）で確かめる
- error log は `getLogger()`（shared-kernel）で出す。テストは `setLogger(new MemoryLogger())` で差し替えて確かめ、`afterEach` で戻す

## 逸脱

- **`docs/domain/janken/hand-手と勝敗.md` に `HandKind`・`OutcomeKind` を列挙型として描き足し、章を足した**（設計では「生き資料の同期は不要」としていた）。`check:model-trace` は domain 層のファイルがどのモデル図にも登場しないことを図の更新漏れとして止める。型だけのファイルも 1 ファイル 1 概念で分けたため、図にも載せた。ステレオタイプは `<<列挙型>>` で、Value Object ではないため describe は要求されない
- **`describe("kind")` を足した**（設計では各 factory のテストの中で確かめるとしていた）。`kind()` は getter 構文（`get kind`）ではなくメソッドなので、`check:model-trace` は図の `+kind()` に describe を要求する。メソッドにしたのは rules/development/project.md の「状態と同じ名前の getter（`#kind` と `kind()`）」に合わせるため
- **`rules/model-design/project.md` に列挙型の描き方と配色（シアン）を追記した**。標準の配色に列挙型が無く、Value Object の緑で塗ると振る舞いを持つ値と見分けられないとレビューで指摘されたため

## 修正ループの記録

- 1 周目のレビューで収束（要修正の指摘なし）。minor 4 件をすべて任意で直した
  - `pickByRandomValue` を添字の計算から区間の比較にし、到達しない防御分岐（ログ無しの throw）を無くした
  - 列挙型を Value Object と別の色で塗った（上の逸脱）
  - 拒否のテストで呼び出しを 1 回にし、ログが 1 件であることまで確かめる
  - 境界の直前の値を、境界より小さい最大の倍精度の値にした
