# 設計メモ: 1.5.1 じゃんけん画面の表示

> 置き場: `.designs/REQ-001-janken/UC-01-janken-battle/impl/1.5.1-design.md`
> 実装ループの設計工程の成果物です。タスクの観測点・入力は [tasks.md](../tasks.md)、画面デザインは [mockups/janken-design.html](../mockups/janken-design.html) にあります。

## 1. 実装方針

### application の DTO（`packages/janken/src/application/GameView.ts`）

画面が表示に使う値だけを持つ型。domain の型（`HandKind` など）は再 export せず、DTO 側で文字列の型を定義する（公開 entrypoint は domain を export しない。docs/architecture）。

- `HandName = "rock" | "scissors" | "paper"`、`OutcomeName = "win" | "lose" | "draw"`
- `OutcomeTally`: `{ count: number; percentage: number | null }`。`percentage` が `null` は「計算できない割合」（UC-01 要件 13 の「-」の元）
- `BattleRecordView`: `{ win; lose; draw }`（それぞれ `OutcomeTally`）
- `RoundView`: `{ playerHand; opponentHand; outcome }`
- `GameView`: `{ record; lastRound: RoundView | null; acceptsHand: boolean; canRematch: boolean }`。画面はボタンを出すかどうかを `acceptsHand`・`canRematch` で決め、自分で判定しない

`packages/janken/src/index.ts` から上の型を `export type` する。DTO への変換（domain → DTO）は 1.6.1 の application service が持つ。

### presentation（`apps/web/src/components/`）

表示 component は DTO と操作のコールバックだけを props で受ける。状態を持たない。

- **`handDisplay.ts`**: 手の名前（グー・チョキ・パー）と絵文字の対応。手のボタンと勝負の結果の両方が使うため独立させる（索引に無いファイル。逸脱を参照）
- **`BattleRecordPanel`**: 勝ち・負け・あいこの 3 枠。各枠に名前・「N回」・割合（「N%」、計算できないときは「-」）。枠は `role="group"` と `aria-label`（勝ち・負け・あいこ）で区別できるようにする
- **`HandButtons`**: グー・チョキ・パーの 3 ボタン。押すと `onSelectHand(hand)`。絵文字は `aria-hidden` にし、ボタンの名前は文字（グー など）にする
- **`RoundResult`**: あなたの手・相手の手（絵文字と文字）と、勝敗の文言（勝ち・負け・あいこでしょ！）。勝敗は色に加えて文字で示す
- **`JankenScreen`**: 画面全体。見出し「じゃんけん」、戦績、直前の勝負があれば勝負の結果、`acceptsHand` なら手のボタン（直前の勝負が無いときだけ「じゃんけん…手を選んでね」を添える）、`canRematch` なら「もう一度勝負する」ボタン
- **`fixtures/gameViews.ts`**: story が使う `GameView` の fixture（手の選択・あいこ・勝ち・負け）
- **`styles.css`**: デザインの配色と配置（スマートフォン幅 360px でも手のボタンが 3 つ横に並ぶ）

## 4. テスト計画

観測点は story（play 関数を Vitest 上で実行）。受け入れ基準 ID は置かない。ID は 1.6.1 で UI 結合テストに置き、そこで「（未実装）」を外す（まだ外さない ID をコメントに書くと `check:trace` が状態マークの矛盾として止める）。

| story | 確かめること |
| --- | --- |
| `BattleRecordPanel`: 戦績 0 回 | 3 枠とも「0回」と「-」 |
| `BattleRecordPanel`: 割合あり | 回数と「N%」。合計が 100 にならない値もそのまま出す |
| `HandButtons`: 手の選択 | 3 つのボタンがあり、押すと押した手でコールバックが呼ばれる |
| `RoundResult`: 勝ち・負け・あいこ | 両者の手の名前と、「勝ち」「負け」「あいこでしょ！」 |
| `JankenScreen`: 手の選択 | 手のボタン 3 つと案内文があり、「もう一度勝負する」が無い |
| `JankenScreen`: あいこ | 両者の手と「あいこでしょ！」、手のボタンがあり、「もう一度勝負する」が無い |
| `JankenScreen`: 勝ち・負け | 両者の手と勝敗、「もう一度勝負する」があり、手のボタンが無い。押すとコールバックが呼ばれる |

presentation は 100% 必須ではないが、story で全分岐を通す。

## 5. リスク・注意点

- 絵文字の表示はフォントに依存する。読み上げとテストは文字の名前で行い、絵文字には依存しない

## 逸脱

- **`apps/web/src/components/handDisplay.ts` を足した**（索引では 12 件、実際は 13 件）。手の名前と絵文字の対応を、手のボタンと勝負の結果の両方が使う。片方に置くともう一方がその component に依存するため、表示の対応表として分けた

## 確認したこと（観測点の外）

- Storybook のビルド（`storybook build`）が通り、`JankenScreen` の 4 状態を幅 360px のブラウザで撮影して、画面デザインどおりに並ぶことを目で確かめた

## 修正ループの記録

- 1 周目のレビューで収束（要修正の指摘なし）。minor 5 件のうち 3 件を任意で直した
  - 読み上げの領域（`aria-live`）を `JankenScreen` に常に置き、案内文と勝負の結果をその中で入れ替える
  - 戦績の枠全体に `role="group"` を付け、「戦績」という名前が読み上げられるようにした
  - story の `roundOf` の型を DTO の型（`GameView`・`RoundView`）で書いた
- 見送った minor
  - モジュール直下の対応表（`handDisplays` など）が camelCase: 既存の domain の対応表（`beatenKindOf`）と書き方をそろえた。規約の解釈（対応表は camelCase か）は、人のレビューで判断を仰ぐ
  - `handDisplay.ts` に単体テストが無い: 表示の対応表で、`HandButtons` と `RoundResult` の story が 3 つの手すべてを通すため置かない（PR に明記する）
  - 同じ手の組であいこが続くと読み上げの中身が変わらない: 1.6.1 の組み込みで扱う
